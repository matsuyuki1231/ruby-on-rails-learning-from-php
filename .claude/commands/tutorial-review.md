学習者が書いたコードをレビューしてください。動くコードを「より Ruby / Rails らしく」するのが目的です。

## 手順

1. レビュー対象を決める
   - 引数で指定されていればそれ
   - 無ければ `git status` と `git diff` で最近の変更を見る
2. 対象ファイルを読む
3. 下の観点でレビューする

## 観点

### Ruby

- `for` 文を使っていないか（`each` / `map` を使う）
- 不要な `return` を書いていないか
- `if` を式として使えていないか
- 述語メソッドに `?` が付いているか
- ブロックの `{}` と `do...end` を使い分けているか（1 行なら `{}`、複数行なら `do...end`）
- `&:method` で短く書ける箇所はないか
- `nil` チェックが冗長でないか（`&.`、`||`、`presence` が使えないか）

### Rails

- URL の直書きが無いか（パスヘルパーを使う）
- ビューに業務ロジックが漏れていないか（ヘルパー / モデルへ）
- コントローラが太っていないか（`scope` へ寄せる）
- Strong Parameters が適切か
- N+1 の可能性はないか
- `Current.user` 経由でデータを辿っているか（他人のデータが見える設計になっていないか）
- 命名が Rails の規約に沿っているか（モデルは単数、コントローラは複数）

## 伝え方

良い点を先に、必ず 1 つ以上挙げてください。学習の継続にはこれが効きます。

指摘は次の形式で。**重要度の高い順に、多くても 5 件まで。**

```
### （指摘の見出し）

**いまのコード**: （該当箇所を引用）
**なぜ気になるか**: （理由。「そういう決まりだから」ではなく仕組みから説明する）
**どう書けるか**: （改善例。ここは具体的なコードを書いてよい）
```

## 注意

- レビューであって、代わりに直すことではありません。**勝手にファイルを編集しないでください**
- 動いているコードを否定しない。「動くが、こう書くともっと Rails らしい」という姿勢で
- 好みの問題（スタイル）と、実害がある問題（セキュリティ、N+1）を区別して伝える
